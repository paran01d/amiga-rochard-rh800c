# Autoconfig

This page explains how the RocHard RH800C announces itself to the Amiga through
Zorro II autoconfig. It covers the original HD-controller board, which the
factory ROM and TTL handle, and the second, **RAM** board. Our rebuilt UA6
presents that RAM board.

Background reading: [Hardware overview](hardware-overview.md) for the chips
and switches, and [RAM subsystem](ram-subsystem.md) for what happens once the
RAM window is mapped.

---

## Zorro II autoconfig in one paragraph

After reset, each unconfigured board in the chain answers at `$E80000` while
its `/CFGIN` is low. The OS reads the board's identity **one nibble at a time
on D15-D12**. Each register byte is split across two word addresses: the high
nibble at offset `4n` and the low nibble at `4n+2`. All registers are stored
**inverted** except `$00/$02` (er_Type) and `$40/$42`. To configure the board,
the OS writes the base address: first the low nibble at **`$4A`** (A19-A16),
then the high nibble at **`$48`** (A23-A20). The `$48` write is the one that
counts. A write to `$4C` tells the board to "shut up" (stay unconfigured). Once
configured, the board asserts `/CFGOUT` and the next board in the chain
answers at `$E80000`.

The decoded identity is often shown as a 16-byte buffer, in this order:
er_Type, er_Product, er_Flags, reserved, er_Manufacturer (2 bytes),
er_SerialNumber (4 bytes), er_InitDiagVec (2 bytes), and 4 reserved bytes.
DiagROM displays it in this form.

## The HD board

### $E8 decode

The HD board's address decode is ordinary TTL. It is the same before and
after configuration; only the comparator's reference value changes.

```
  A16-A23 --U3 '245--> AB16-AB23 --> U10 74LS688 "P" inputs
                                        |
  U10 "Q" (reference) inputs <----------+---- U9 74LS374 Q outputs (Hi-Z until configured)
        ^             ^                 |
        |             |                 +---> /_CFGADDR_MATCH --> U13 / U14 (ROM, IDE)
   RN1 pull-ups   RN2 pull-downs
   AB19,21,22,23  AB16,17,18,20
     (the 1-bits)   (the 0-bits)
        = $E8 = 1110 1000
```

- **Before configuration**, U11's `_BUFRDY` (o20) is high. That holds U9's
  `/OE` high, so U9's outputs are Hi-Z. U10's reference is then set only by the
  resistor networks: RN1 pulls the AB19/21/22/23 reference pins high and RN2
  pulls the AB16/17/18/20 pins low. The result is **$E8**, so U10 matches in
  the autoconfig space.
  The schematic draws RN2's common on +5 V. On the real board it goes to GND.
  We confirmed this with a scope on a powered card.
- **The base write.** U11 o21 (`/BASE_C`, active high despite the name) sets
  when it sees the `$48` write while `/_E8WIN` is low, and then holds itself
  set:

  ```
  o21 = /i1 & /i4 & i6 & /i7 & /i8 & i9 & /i10 & /i11 & i13 & /i19 & /i23
      + i13 & o21
  ```

  `/BASE_C` clocks U9, which latches D8-D15 (the base byte A23-A16 the OS just
  wrote). `_BUFRDY` (o20) then goes low and enables U9's outputs.
- **After configuration** U10 compares the address bus with the assigned
  base. On our card that is `$E9`: U10 pin 3 (AB16) rises from 0 V to about
  3.4 V, which is U9 driving high against RN2's pull-down.

UA4 generates the autoconfig window strobe `/_E8WIN` (o23):

```
/o23 = /i14 & i15 & /i20      ; i14 = /_DRVEN (from UA6), i15 = _AS, i20 = /_BANK_SEL (SW1)
     + /i14 & /o23            ; self-hold
```

`/_E8WIN` can only open while **`/_DRVEN` is low** and the Game switch grounds
`/_BANK_SEL` (position II). It can only *assert* while `_AS` is high, that is,
between bus cycles. This is why UA6's `/_DRVEN` controls whether the HD board
is visible at all.

**DIP-1 (HD enable) also gates autoconfig.** With DIP-1 OFF the card does not
appear in the chain.

### The HD board: ROM-served identity

None of the HD board's identity is generated by logic. The boot ROM (U6/U20)
drives it onto DB12-DB15 whenever the autoconfig window is decoded and U14
asserts `/_ROMOE`. WinUAE emulates the card the same way: it copies the
autoconfig bytes out of the ROM image.

Known-good buffer read by DiagROM from our working card (autoboot ROM half):

```
D1 01 40 00 08 60 00 00 04 D2 00 80 00 00 00 00
```

| Bytes | Field | Value | Meaning |
|---|---|---|---|
| `D1` | er_Type | `$D1` = `11 0 1 0 001` | Zorro II, not memory, **DIAGVALID** (boot ROM present), not chained, size code 001 = **64 KB** |
| `01` | er_Product | 1 | RocHard HD controller |
| `40` | er_Flags | `$40` | bit 6 set (ERFF_NOSHUTUP: the board cannot be shut up) |
| `00` | reserved | | |
| `08 60` | er_Manufacturer | `$0860` = **2144** | Roctec |
| `00 00 04 D2` | er_SerialNumber | `$000004D2` (1234) | |
| `00 80` | er_InitDiagVec | `$0080` | offset of the DiagArea in the ROM |
| `00 ...` | reserved | | |

With **DIP-3** set for Kickstart 1.2, the other ROM half is selected. It
differs only in word 0, so er_Type reads **`$C1`**: DIAGVALID is clear, so
Kickstart does not run the boot code and the board is an ordinary I/O board.

> **Read the whole buffer.** DiagROM's one-line summary once showed "2144/0",
> which we wrongly took as evidence that DB12 was stuck high. The full buffer
> was perfect. Always compare the full 16 bytes.

## The RAM board, presented by our UA6

### Why a second board is needed

The fast RAM is a Zorro II memory board, **manufacturer 2144, product 2**.
WinUAE's description of this card (`rochard_sub[]`) gives the same identity.
Kickstart only adds memory it has been told about, so if nothing presents the
RAM board, the RAM works but never appears in the free memory list. We saw
exactly this with the HD-only UA6 builds: ATK's direct memory scan found 2 MB at
`$200000`, but Kickstart's memory list did not include it.

The ROM cannot provide this identity. It only ever serves the HD board's
bytes. We could not recover the original UA6's logic, because a black-box
sweep cannot see GAL22V10 internal feedback. So we designed a new UA6 from
first principles: [`ua6_ram6.pld`](../gal/ua6/ua6_ram6.pld). It modifies no
other original chip; everything is done through UA6's own pins.

### The levers UA6 has

| UA6 pin | Signal | Use |
|---|---|---|
| 1-6 | AB1-AB6 | Autoconfig register offset |
| 7 | `GALSTB` = `/_GALSTROBE` from UA4 | Asserted on `$E8` cycles while `/_DRVEN` is high **and** a RAM size strap is fitted |
| 8 / 9 / 10 | RCFG8 / RCFG4 / RCFG2 | JPA1 size straps (active low) |
| 11 | `BASEA` = U12's `BASE_A` | `_AS` registered twice: a mid-cycle timing reference (about 280 ns into a 560 ns cycle) |
| 13 / 14 / 17 | RW, `/CFGIN`, `RST` | |
| 18-21 | DB15-DB12 | Nibble drivers |
| 22 | NC22 | **Unconnected pad**, used as an internal state latch |
| 23 | `/_DRVEN` | To UA4 pin 14, with no pull resistor |

`/_DRVEN` is the key output. UA4 needs it **low** to open `/_E8WIN`, and with
`/_E8WIN` closed the ROM is silent. So holding `/_DRVEN` **high**:

1. closes `/_E8WIN`. U10 is then disabled, `/_CFGADDR_MATCH` stays high, and
   U14 releases `/_ROMOE`, so **the ROM stops driving DB12-15**;
2. puts UA4's base latch o16/o17/o18 (`.oe = /i14`) into **capture mode**.
   These are `/_CFGD15/14/13`, wired to DB15/14/13;
3. arms UA4's strap-gated `/_GALSTROBE` terms, which mark every `$E8` cycle as
   a RAM-board cycle.

UA4's three-bit latch then sets **where the RAM window decodes** (`/GALCLK1`,
o19). It holds A23/A22/A21 of the RAM base:

| Latch (o16,o17,o18) | Window | Result |
|---|---|---|
| **(0,0,1)** | **`$200000`** | Correct |
| (1,1,1) | `$E0`-`$FF`, including `$F8` Kickstart | Bus contention, red screen / freeze |
| (1,1,0) | `$D8` | Yellow screen |
| (1,0,1) | `$A0` | Wrong |
| (0,0,0) | none | RAM never answers, so Kickstart marks the board "defective" |

### The sequence

```
reset
  |  UA6: /_DRVEN HIGH  (ROM silent, UA4 latch in capture mode)
  v
Board 1 = RAM (UA6 drives DB12-15 as a function of AB1-AB6 and the straps)
  |  OS reads er_Type $EE/$EF/..., writes base to $4A then $48
  |  UA6 drives (0,0,1) on DB15/14/13 during the $48 write
  |  UA6 sets NC22 mid-cycle (gated on /BASEA) -> /_DRVEN LOW
  |  UA4 latch closes on (0,0,1) = $200000 window
  v
Board 2 = HD (ROM back on, /_E8WIN can open, normal ROM-served identity)
  v
Kickstart adds 2/4/8 MB (8 MB untested) fast RAM at $200000 and boots
```

### RAM board identity

```
er_Type = $C0 (Zorro II) | $20 (MEMLIST: add to free pool) | $08 (CHAINEDCONFIG) | size
          2 MB -> $EE      4 MB -> $EF      8 MB -> $E8
er_Product 2   er_Flags 0   er_Manufacturer 2144   serial 0   InitDiagVec 0
```

After inversion almost every nibble is `$F`, so UA6 only ever **pulls bits
low**. Its outputs are active-low with a default of HIGH:

| Offset | Nibble | Why |
|---|---|---|
| `$00` | `E` | er_Type high nibble (not inverted) |
| `$02` | `E` / `F` / `8` | er_Type low nibble, from the strap: 2M / 4M / 8M |
| `$06` | `D` | er_Product 2, inverted = `$FD` |
| `$12` | `7` | Manufacturer high byte `$08`, inverted = `$F7` |
| `$14` | `9` | Manufacturer low byte `$60`, inverted = `$9F` |
| everything else | `F` | zeros, inverted |

DiagROM read our board back with every byte as designed:

```
Board #1  Manufacturer: 2144  Serialnumber: 0
  Zorrotype: II   Link to system free pool: YES   Autoboot: NO   Size: 2MB
  Autoconfigbuffer: EE 02 00 00 08 60 00 00 00 00 00 00 00 00 00 00
  Zorro II Memory detected and assigned to: $00200000 - $003FFFFF
```

> **8 MB er_Type.** The equations in `ua6_ram6.pld` produce nibble `8` at
> `$02` for the 8M strap, so the board reads **`$E8`** (Zorro II + MEMLIST +
> CHAINED + size code 000). **The 8M strap has never been tested on
> hardware;** 2M and 4M (`$EE`, `$EF`) have.

### The equations (rev 6)

The phase latch lives on the unconnected NC22 pad. Once set, it is held by a
term that depends on nothing but reset:

```
/NC22.T = /GALSTB & /RW & AB6 & /AB5 & /AB4 & AB3 & /AB1 & /BASEA & RST   ; set: $48 (or $4C) write, mid-cycle
        + /NC22 & RST                                                     ; hold
```

`/_DRVEN` follows the latch. It holds itself too, and has an escape term for
cards with no RAM strap fitted:

```
/DRVEN.T = /NC22 & RST                                    ; RAM phase finished
         + /DRVEN & RST                                   ; self-hold, cleared only by reset
         + /CFGIN & /BASEA & RST & RCFG2 & RCFG4 & RCFG8  ; no strap (DIP-2 off): skip the RAM board
```

The nibble drivers are enabled only in the RAM phase, on `$E8` cycles:

```
DB15.E  = /CFGIN & /GALSTB & DRVEN
/DB15.T = /AB6 & /AB5 & AB4 & /AB3 & /AB2 & AB1              ; $12 -> 7
        + /GALSTB & /RW & AB6 & /AB5 & /AB4 & AB3 & /AB1     ; base write: drive 0
```

`DRVEN` is part of every output enable. This matters because once `/_DRVEN`
drops, `/_GALSTROBE` also fires for ordinary `$200000` RAM accesses. Without
`DRVEN` in the enable, UA6 would drive the data bus during every RAM read.

DB13 deliberately has **no** base-write term. It stays HIGH during the `$48`
write, which gives the latch value (0,0,1).

### Design rules learned the hard way

- **Do not sample the CPU's write data; drive it.** The base value is on the
  bus for about one 62 ns sample before the latch has to close. UA6 therefore
  drives (0,0,1) itself during the `$48`/`$4C` write. This hard-wires the RAM
  base to `$200000`. That works because the RAM board configures first, and
  Kickstart assigns the first Zorro II memory board to `$200000`. A system
  that already had another Zorro II memory board configured earlier in the
  chain would break this assumption.
- **Anything gated on `/_GALSTROBE` dies the instant `/_DRVEN` drops,**
  because UA4's strap-gated GALSTB terms need `/_DRVEN` high. Whatever must be
  valid when UA4's latch closes cannot depend on GALSTB unless the drop is
  delayed. `/BASEA` is the only mid-cycle delay UA6 has.
- **`/BASEA` is a per-cycle strobe, not a level.** Any term gated on it needs
  a self-hold, or the output just follows the bus.
- **Keep the hold path free of anything external.** A latch whose set term is
  killed by its own effect (DRVEN low, then GALSTB high, then the set term is
  gone) never sticks.

### Testing an autoconfig change

1. **Regression first: DIP-2 OFF.** The HD must still autoboot exactly as
   before. The no-strap escape term handles this case.
2. DIP-2 ON, JPA1 = 2M, SIMM0/1 fitted. Boot DiagROM and read the full
   autoconfig buffer. Expect `EE 02 00 00 08 60 ...` and then the HD board's
   `D1 01 40 00 08 60 ...`.
3. When DiagROM asks whether to assign the board, answer **Y**. With N or ESC
   no base is written, so the RAM phase never ends and re-scanning lists the
   RAM board twice and no HD board. That is DiagROM's behaviour, not a card
   fault.
4. If you have a logic analyser, check UA4's latch (`/_CFGD15/14/13`, UA4 pins
   16/17/18) right after `_E8WIN` falls. It must read (0,0,1).
   [`../la-tools/rh_acprobe.py`](../la-tools/rh_acprobe.py) decodes autoconfig
   cycles from a capture, and
   [`../la-tools/AUTOCONFIG_PROBE.md`](../la-tools/AUTOCONFIG_PROBE.md) gives
   the channel map.

> **Validate the logic-analyser rig before trusting a capture.** Many of our
> "stuck" signals were dead or misplaced probe clips. Free-run for a second
> and confirm every channel toggles. The ferrite beads FB3-FB12 make good,
> isolated probe points for J1 control signals.
